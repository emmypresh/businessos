# Phase 1N — Management Dashboard and Reporting Aggregate Architecture

## 1. PRD
**User/problem.** Owners and financial managers need a trustworthy starting view without raw operational rows. **V1 goal.** A protected overview provides the established 30-day financial summary plus transparent, defensible management indicators. **Non-goals.** No write path, health score, profit/COGS/margin, forecast, inventory value, campaign metric, or fabricated KPI. **Acceptance.** An active member with `reports.view` sees only server-authorized aggregates; without it, neither aggregate call is made. WhatsApp follow-up is omitted unless the same caller holds `whatsapp.view`. Loading, empty, failure, and recovery use the existing route boundary and Financial overview.

## 2. Technical design
The server-rendered business root uses the trusted permission set before calling cached server DAL functions. The additive `public.get_management_reporting_aggregate` is stable `SECURITY DEFINER`, has `search_path = ''`, is owned by a dedicated `BYPASSRLS` reader with exact column grants, repeats `reports.view` authorization, and grants execute only to `authenticated`. Its private implementation pins `TimeZone = 'UTC'`, so timestamptz-to-date daily boundaries cannot depend on a caller session. It returns a bounded JSON aggregate, never rows. No client secret, browser RPC, cache persistence, mutation, or third-party integration is added.

## 3. App flow and state map
`/[businessId]` → active membership → permission set. With `reports.view`: resolve UTC Last 30 Days → concurrently load financial and management aggregates → render cards → Financial overview link. Without it: existing welcome only. On mobile cards stack; keyboard reaches the semantic link; a server failure reaches the existing error boundary. Optional WhatsApp card appears only when its count is non-null.

## 4. UI/UX brief
Existing cards retain neutral surfaces, one accent, tabular numbers, visible focus, semantic headings, responsive grids, and 44px link controls. Labels describe evidence, not judgement: “unsold with stock” rather than a made-up risk score. No chart or queue is displayed without a returned aggregate.

## 5. Backend/data design
**Period contract.** Inputs are UTC `[from, to)` instants. The preceding comparison period is the adjacent equal duration `[from - (to-from), from)`; daily grouping uses `completed_at AT TIME ZONE 'UTC'` and the implementation function pins `TimeZone = 'UTC'` for its timestamptz-to-date series bounds. No business timezone exists, so local calendar assumptions are not claimed.

**Sources/definitions.** Daily revenue is completed `sales.total`; order count is completed sales; AOV is revenue/order count (zero on no orders). New customers are `customers.created_at` in the current period. Returning customers have a current completed sale and one earlier completed sale; repeat customers have two or more current completed sales; anonymous sales are excluded. Current stock sums balances at active locations for active tracked products: out-of-stock is zero, low stock is `0 < quantity <= explicit threshold`, and unsold-with-stock is positive stock with no current-period completed sale item. Branch revenue/count uses completed sales attributed to an accessible branch. WhatsApp follow-up is an OPEN conversation whose latest recorded direction is inbound (`last_inbound_at` exists and is later than `last_outbound_at`, or no outbound exists); it is not an SLA or priority score.

**Branch/permission contract.** The frozen business-wide `reports.view` policy remains intact for financial totals. The new branch *breakdown* is intentionally narrower: only active tenant branches where `private.has_branch_access(business_id, branch_id)` is true are emitted. This uses current active membership plus branch assignment, never role names. Inactive-branch historical financial reporting remains available through the frozen scoped financial RPC but is not presented as current branch activity. WhatsApp counts additionally require `whatsapp.view`.

**Deferred.** Profitability/COGS/margin, inventory value, product trend detail, customer LTV, forecasting, business health score, unassigned-branch ranking, and WhatsApp priority/SLA/provider-ingestion metrics.

## 6. Engineering plan
1. Maintain one UTC comparable-period helper. 2. Add the bounded reader RPC and typed DAL. 3. Preserve `reports.view` route/RPC defense and separately gate WhatsApp. 4. Render only named supported definitions. 5. Prove authorization, tenant isolation, boundaries, branch assignments, formulas, and non-UTC-session invariance with integration tests. 6. Run migration/test/lint/type/build/diff gates. Rollback is a forward migration resetting the implementation function timezone plus removing execute/function and the dashboard call; no data recovery is required.
